# SUPER implementation phases

This is a delivery sequence, not a claim that the full platform is complete. Each module is finished only when it is integrated on `main`, tested in CI, documented, and checked for failure behavior, security, and performance appropriate to its scope. Build original implementations from the repository's contracts; reference repositories inform design but are not cloned into SUPER.

| Phase | Modules | Completion evidence |
| --- | --- | --- |
| 1. Runtime operations | Readiness, configuration, resource admission, safe shutdown, supervision and failover (reconcile #52–53) | Real lifecycle wiring, bounded checks, concurrent admission tests, restart/failure tests, measured overhead |
| 2. Request safety | Trusted identity, rate limits, durable idempotency and atomic single-flight (#54–57) | Multi-process and crash tests, explicit replay and rejection contracts, bounded memory |
| 3. Observability | Event transport, durable log, checkpoints, synchronization, gap repair and integrity (#58–69) | Replay and corruption tests, convergence after partitions, retention and throughput evidence |
| 4. Remote execution | Durability, protocol, identity, attestation, effect ledger and coordination (#91–97) | Authenticated cross-process workers, lease fencing at the side-effect boundary, fault injection, latency budgets |
| 5. Mission integration | Recovery and observability integration; reconcile #98–104 | End-to-end mission tests through interruption, restart, duplicate delivery and verification |
| 6. Tool and reverse engineering fabric | Governed filesystem, terminal, Git/GitHub, browser, HTTP, MCP and dedicated investigators for new target types | Permission and sandbox tests, provenance and evidence checks, resource bounds for each adapter |
| 7. Knowledge and intelligence | Durable memory, retrieval, document/code graphs, real model/harness adapters | Evaluated answer quality, source provenance, privacy and provider interoperability |
| 8. Platform and evolution | Studio, workflows, plugins, domain packs, experiment and promotion systems | Usable vertical workflows, benchmark regressions, rollback, security and accessibility gates |

Work on a module in focused PRs rather than merging a historical stack wholesale. If an older PR's behavior is fully replaced and verified, close it with its replacement linked. Do not equate passing unit tests with cross-process guarantees or production readiness.

Phase 2 progress: `ControlPlaneGateway` and `RuntimeGatewayDeployment` accept an optional `RuntimeRequestGuard`. Authorization runs before admission; the guard uses the actual socket address for its default identity, rejects excess requests, holds duplicate commands while one is running, and replays committed HTTP responses. A configured distributed limiter and durable idempotency store can extend these decisions across processes. Without them, limits and replay are local to the gateway instance. A failure to commit an idempotency response returns 503; the pending claim is retained after expiry because the command may already have executed. The Linux durable store now holds a kernel `flock` on an inherited file descriptor for each transaction; a short child acquires it, while the parent keeps the descriptor open until its journal operation finishes. A killed owner releases the lock. A local 12-claim comparison measured approximately 37 ms with this design versus 20 ms for the former directory lock and 805 ms for a separate Node transaction helper; this is a small overhead sample rather than a throughput claim. The lock file must remain at its configured path and this implementation requires Linux and the `flock` utility. Stop all older directory-lock processes before upgrading a shared journal because the old and new lock paths differ. Do not put raw forwarded identity headers into a trusted client key.

`FileRateLimiter` is an opt-in shared fixed-window implementation for the request guard. Configure the same file path, window size, and request limit on every process; one Linux kernel lock serializes state reads and atomic replacements. It hashes principals in the stored state, bounds retained principals, rejects corrupt or missing previously observed state, and keeps request decisions across restarts. The guard maps store errors to a fail-closed 503. A local 12-consume sample took approximately 49 ms; the default in-memory guard remains the faster choice when cross-process coordination is unnecessary. The file implementation requires a shared local filesystem with reliable `flock` semantics and is not a network-distributed rate service. Clock agreement matters across processes, and a response may have been allowed before an abruptly killed process writes its result; the counter is committed before `consume()` returns. A per-principal token bucket, identity-aware proxy integration, and load testing remain future work.

Expired pending idempotency claims now return `recovery_required` and the gateway responds with `IDEMPOTENCY_RECOVERY_REQUIRED` (409) without rerunning the command. The durable store preserves those claims through restart and compaction; its bounded record capacity can fill until an operator reconciles them. After verifying the external effect, an operator can call `reconcileClaim(key, fingerprint, token, response, { reason })` to record a replayable response, or `releaseClaim(key, fingerprint, token, reason)` only after confirming that no effect occurred. Both require the original token and an expired claim; normal completion rejects stale tokens. Direct deletion of pending claims is blocked. The in-memory guard also blocks expired claims during its process lifetime, but cannot survive a restart. Existing pending claims from older journals become blocked on upgrade and need reconciliation. This protects duplicate dispatch; it cannot determine whether an external effect occurred or undo one already committed.

`RuntimeBearerAuthorizer` is an optional concrete gateway authorization callback for opaque bearer tokens. A caller supplies `credentials()` that returns bounded `{ digest, principal, expiresAt, notBefore? }` entries; `digest` is the lowercase SHA-256 hex digest of a high-entropy token. The adapter checks a bounded token syntax, compares digests with constant-time byte comparison, and reads the provider on every request so rotation or revocation takes effect on the next call. It returns only the verified principal; its snapshot contains no credentials. The gateway removes Authorization and Proxy-Authorization headers before passing a request to its guard or command handlers. The provider must store digests outside public runtime configuration and serve a coherent list, and the listener must use TLS at the deployment boundary because bearer tokens grant access when disclosed. Invalid headers and expired tokens are denied, and provider failures fail closed. `ControlPlaneGateway` and `RuntimeGatewayDeployment` accept an optional `preAuthLimiter` with `consume(principal)`, called on the actual socket address before authorization. A shared `FileRateLimiter` can bound attempts across local processes, including invalid tokens; limiter failures return 503 without calling the credential provider. This optional limit charges every request, including successful requests and local health checks. Deployments choose its quota separately from the authenticated request guard.

Trusted proxy identity uses an explicit list of proxy IP addresses. When enabled, `RuntimeRequestIdentity` walks a bounded, validated `X-Forwarded-For` chain from the socket toward the client and selects the nearest untrusted hop; malformed or oversized chains fall back to the socket address. Pre-authorization admission always charges the socket address. Configure only proxies that overwrite or correctly append forwarding headers, and keep authenticated principals authoritative when available.

The in-memory request guard bounds active rate windows with `maxRateWindows` (default 10,000), fails closed on capacity, and reclaims expired windows. Expired completed replay records are reclaimed at capacity or on direct lookup; pending ambiguous claims remain retained. Routine admissions avoid scanning every retained principal, preserving constant work for the local guard until cleanup is needed.

Phase 2 local verification: `node scripts/benchmark-phase2.mjs 100` on Linux/Node 24.22.1 measured local guard median 0.01 ms (p95 0.03 ms, approximately 79,922 decisions/s), shared file rate limit median 3.89 ms (p95 6.46 ms, approximately 228 decisions/s), and durable claim plus completion median 5.44 ms (p95 8.51 ms, approximately 169 pairs/s). These are sequential local samples, not a concurrent service capacity guarantee. The tests cover multi-process contention, process death, stale claims, corrupt state, proxy spoofing, credential rotation, and replay. The local Phase 2 modules are integrated; multi-host coordination, TLS termination, credential storage, proxy deployment policy, and sustained production load tests remain deployment concerns.

The gateway authorization callback can return `{ allowed: true, principal: 'verified-user' }` to bind the request guard, replay key, and command context to an authenticated principal. Boolean `true` continues to authorize local traffic, which falls back to the socket address for guard identity. Raw `clientKey`, forwarding headers, and client ID headers do not establish a trusted gateway principal. A non-loopback listener requires an explicit authorization callback that returns a verified principal for each accepted request; returning only `true` receives 403. The callback must verify the credential or upstream authentication itself, and deployments must keep principal values stable across processes. Authentication providers, credential rotation, and trusted proxy integration are deployment-specific future work.

Phase 3 starts with opt-in `RuntimeEventTransport`: bounded asynchronous publishing, ordered event delivery, independent subscriber copies, explicit capacity rejection, and drain on close. It is in-process and does not provide durable replay or cross-process delivery; those boundaries are next. The existing synchronous `EventBus` remains the local low-overhead path.

Current phase 1 progress: local coordination is integrated through #121, bounded readiness through #122, resource reservations through #123, tool execution admission through #124, and validated non-secret configuration through #125. The local shutdown gate closes tool dispatch and central capability execution on drain and keeps leases until handlers settle (#126–127). `RuntimeShutdownCoordinator` orders lifecycle startup, admission opening, drain, and component stop (#128). The local supervisor evaluates bounded dependency health (#129). Opt-in SIGINT/SIGTERM handling coordinates bounded drain (#130). Task graphs (#131) and execution plans (#132) admit the full run before state changes, including resume. `MeasuredProcessRuntime` offers opt-in measured CPU/heap enforcement (#133) and optional Linux RSS sampling (#139). `FileFailoverStore` provides cross-process, epoch-fenced claims and commits under Linux flock (#134). `RuntimeFailoverKernel` performs incident-scoped, supervisor-triggered recovery with heartbeat, cancellation, deadline, and committed outcome (#135). Lifecycle startup rolls back components that successfully started, and stop attempts every component even if one fails (#136). `RuntimeDeploymentHost` composes lifecycle, bounded incident polling, failover attempts, and drain, with optional signal wiring (#137). Local file effects can enforce the lease at atomic replacement (#138). A killed host takeover test and reproducible process overhead benchmark are included (#140). An opt-in HTTP adapter enforces per-tool request counts (#142). `RuntimeGatewayDeployment` wires a real HTTP listener into lifecycle, admission, supervision and failover (#143). A deployment-specific stable incident provider and recovery adapter are still required; other external effect adapters remain unfenced.

Startup rollback calls stop on components whose start completed, in reverse dependency order. A component whose start throws must clean up its own partial initialization. If rollback or shutdown cleanup fails, restart remains blocked until a subsequent stop successfully cleans up components; operators can inspect `cleanupRequired` in the lifecycle state. Component start and stop handlers must be safe to retry because cleanup after an uncertain failure may revisit a component.

Runtime configuration is limited to validated, non-secret settings with monotonic versions and atomic reload. Secret-shaped fields are rejected; credentials require a separate secret provider and must not enter configuration snapshots or history.

The failover file store writes a persistent `.initialized` marker under its lock before the first state write. An initialized store with a missing state file fails closed even for a new process, preventing epoch reset. Existing valid state files acquire the marker on first access. Keep the marker with the state and lock files; restore lost state from a trusted backup. A crash between marker creation and initial state write also requires repair rather than an unsafe fresh claim.

`FileIncidentProvider` reads a bounded, UTF-8 JSON document `{ "schemaVersion": "0.1.0", "incidentId": "operator-stable-id", "active": true }` through a retained descriptor. A deployment controller must atomically replace this document with a new unique ID for each independent incident; set `active: false` to pause recovery. Point `RuntimeDeploymentHost` or `RuntimeGatewayDeployment` at `provider.provider()`. Missing, corrupt, and oversized files report errors instead of generating a transient incident ID. Reusing an ID after a committed recovery will suppress that recovery, so the publisher must own incident identity and persistence. This is a concrete file-backed provider for a single shared filesystem, not an automatic incident detector or a multi-host consensus service.

For a Linux shared-file deployment, `FileIncidentController` can publish those IDs: `open()` acquires a kernel lock and returns the existing active ID or creates a UUID, while `resolve(id)` deactivates only that matching active ID. Separate processes therefore agree on one active incident, and a later incident receives a new ID. Its initialization marker prevents a missing state file from silently resetting identity after first use. A deployment health detector still chooses when to call `open()` and `resolve()`; do not resolve merely because a recovery callback returned if the underlying failure persists. Keep the state, `.lock`, and `.initialized` files on a filesystem with reliable Linux `flock` semantics.

`RuntimeResourceGovernance` tracks in-process reservations. Its `cpuMs` and `memoryBytes` values represent requested budgets, not measured consumption or OS-enforced limits. `ToolRuntime` can optionally admit a manifest-declared reservation before dispatch and hold it until the handler settles, even if the caller times out. When configured with `BoundedHttpTransport`, a tool receives `context.network.request()`, which charges each attempt against the manifest's `resourceRequest.networkRequests`, restricts exact origins and redirects, bounds response bytes, and forwards cancellation (#142). A caller cannot raise this manifest budget through context. Arbitrary handler use of global fetch, HTTP libraries, or raw sockets bypasses this adapter; hard egress enforcement requires isolation outside the process. `MeasuredProcessRuntime` is a separate opt-in path for trusted JavaScript modules: a child supervises a worker thread's measured CPU and JS heap, while the parent terminates the child on wall deadline and caps concurrent children. On Linux, an optional `rssBytes` cap samples the child process's resident high-water mark, including native Buffer allocations (#139). `createMeasuredProcessHandler` lets a registered tool use this path and forwards cancellation. The child contains a worker heap crash. Sampling can overshoot by one interval, and RSS is measured inside the child rather than enforced by the OS; a very fast or extreme allocation may exceed the cap before termination. This path requires Node 22.19+ for worker CPU measurement, fails closed if a requested measurement is unavailable, and is not a security sandbox or hard network quota. Other tool handlers do not automatically run inside it. Do not use independent resource governors as a shared quota.

Failover callers must supply a stable incident ID and a recovery callback. `RuntimeFailoverKernel` gates callbacks on a failed supervisor evaluation, renews its lease during recovery, and commits an incident result only under its current epoch and token. A later incident ID permits a new recovery. Recovery callbacks receive an abort signal and a fence with `key`, `epoch`, `token`, and `assertCurrent()`. `FileFailoverStore.writeFencedJson(fence.key, fence, destinationPath, value)` is a concrete local file effect boundary: the same Linux lock validates the active lease immediately before atomic replacement, so an expired holder cannot write after takeover (#138). The destination must be trusted configuration, separate from failover state; callers should not accept arbitrary user paths. A network service, database, or other effect adapter must enforce the epoch and token at its own commit boundary. An uncooperative callback may continue its external work after timeout or cancellation, and a completed file effect cannot be rolled back if the recovery result later fails. The deployment host is opt-in and requires a deployment-specific incident provider and recovery callback.

`RuntimeGatewayDeployment` is a concrete local HTTP composition. It starts and stops `ControlPlaneGateway` through lifecycle, keeps an admission lease until each HTTP response finishes or closes, and checks control-plane health through the supervisor. Shutdown rejects new HTTP requests with 503 while active responses drain. The default listener binds 127.0.0.1; another bind address requires an explicit authorization callback. A caller must provide a durable failover store, stable incident identity, and recovery callback suited to its deployment. The composition does not infer incidents from transient health timestamps or automate arbitrary external effects.

Phase 1 evidence: `deployment-host.test.js` kills a process after it claims recovery, starts a replacement host, and verifies takeover after lease expiry. `node scripts/benchmark-phase1.mjs 12` on Linux/Node 24.19.0 measured 12 local samples: claim plus release median 155.04 ms (p95 179.59 ms); measured echo median 123.44 ms (p95 130.95 ms); measured echo with RSS median 125.52 ms (p95 133.36 ms). This small local run is an overhead reference, not a throughput guarantee. Each file store operation spawns a locked helper, and each measured task spawns a child. These paths are opt-in and should not be placed on a high-volume hot path without a persistent coordinator or worker pool and a separate performance review. Native RSS sampling is not a hard memory limit. Phase 1 remains open for deployment-specific adapters and stronger OS-enforced limits where required.
