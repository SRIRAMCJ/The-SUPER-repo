# SUPER implementation phases

This is a delivery sequence, not a claim that the full platform is complete. Each module is finished only when it is integrated on `main`, tested in CI, documented, and checked for failure behavior, security, and performance appropriate to its scope. Build original implementations from the repository's contracts; reference repositories inform design but are not cloned into SUPER.

| Phase | Modules | Completion evidence |
| --- | --- | --- |
| 1. Runtime operations | Readiness, configuration, resource admission, safe shutdown, supervision and failover (reconcile #52–53) | Real lifecycle wiring, bounded checks, concurrent admission tests, restart/failure tests, measured overhead |
| 2. Request safety | Trusted identity, rate limits, durable idempotency and atomic single-flight (#54–57) | Multi-process and crash tests, explicit replay and rejection contracts, bounded memory |
| 3. Observability | Event transport, durable log, checkpoints, synchronization, gap repair and integrity (#58–69) | Replay and corruption tests, convergence after partitions, retention and throughput evidence |
| 4. Remote execution | Durability, protocol, identity, attestation, effect ledger and coordination (#91–97) | Authenticated cross-process workers, lease fencing at the side-effect boundary, fault injection, latency budgets |
| 5. Mission integration | Recovery and observability integration; reconcile #98–104 | End-to-end mission tests through interruption, restart, duplicate delivery and verification |
| 6. Tool and reverse engineering fabric | Governed filesystem, terminal, Git/GitHub, browser, HTTP, MCP and dedicated investigators for new target types | Permission and sandbox tests, provenance and evidence checks, resource bounds for each adapter |
| 7. Knowledge and intelligence | Durable memory, retrieval, document/code graphs, real model/harness adapters | Evaluated answer quality, source provenance, privacy and provider interoperability |
| 8. Platform and evolution | Studio, workflows, plugins, domain packs, experiment and promotion systems | Usable vertical workflows, benchmark regressions, rollback, security and accessibility gates |

Work on a module in focused PRs rather than merging a historical stack wholesale. If an older PR's behavior is fully replaced and verified, close it with its replacement linked. Do not equate passing unit tests with cross-process guarantees or production readiness.

Phase 4 begins with `RemoteWorkerAuthenticator`: a bounded HMAC-SHA-256 request envelope with explicit node and request IDs, timestamp freshness, constant-time MAC comparison, and a nonce replay window. `RemoteExecutionTransport` generates UUID request IDs. `verifyWithStore(envelope, store)` commits the nonce in a shared `FileRemoteNonceStore` before releasing the authenticated body. All local workers sharing a signing key must use the same store and the asynchronous verifier; mixing in the synchronous in-memory `verify()` loses cross-process replay resistance. The Linux store uses a kernel lock and atomic replacement, bounds entries, and fails closed if its initialized state disappears. Keep its marker and lock file with its state file on a trusted shared filesystem. Nonces are retained through the full signed freshness interval, including future-dated requests. This is a single-host control path with a full state read and durable write per request, not a high-throughput distributed nonce service. The authenticator remains a protocol component, not a network listener or worker identity registry. HMAC authenticates requests but does not encrypt them; deploy over a protected channel, keep high-entropy keys outside runtime configuration, and bind worker capabilities to the verified node identity. Remote execution and side-effect fencing remain to be built and verified.

`UnixWorkerServer` and `UnixWorkerClient` add an opt-in local socket transport. The worker requires a private directory owned by its process, accepts one bounded JSON request per socket, verifies the MAC and durable nonce, matches the configured node ID, then invokes only registered capability handlers. The client bounds request and response frames and applies a timeout. Use a dedicated private socket directory and a high-entropy signing key from a separate secret provider; file permissions and this HMAC contract are for a trusted single-host deployment. This transport is not wired into `RemoteExecutionTransport` or mission execution yet. The worker handlers must perform their own policy, audit, durable idempotency, and effect fencing; an authenticated request alone does not authorize arbitrary side effects. A timed-out client does not cancel a handler already executing. Network-host deployment, attestation, response authentication across untrusted directories, and lease-fenced effects remain open.

For configured `effects` capabilities, the Unix worker now injects `context.writeEffect(value)` bound to a trusted destination and a signed lease credential. It calls `FileFailoverStore.writeFencedJson()` so the store checks the epoch and token under the same lock as the atomic file replacement. Missing or stale credentials reject before a file effect; a test replaces a lease and confirms its old holder cannot write. The effect destination is server configuration, never a client path. This is an optional local JSON file effect boundary; handlers that bypass the injected method or perform network/database effects remain outside its fencing guarantee. Policy, audit, idempotency, and mission integration remain open.

The Unix worker requires an explicit `authorize({ capabilityId, nodeId, requestId, input })` callback and a durable audit journal exposing `append()`. A denial or audit-start failure stops the handler. Successful and failed handler outcomes append terminal events with the request and node ID. The authorization callback must use trusted server-side policy and must not treat signed client input as a grant. If terminal audit persistence fails after the handler or effect, the caller receives a failure but the effect may already have happened; reconcile the journal and effect before any retry. Duplicate request IDs with new nonces still require a durable execution idempotency ledger, which is not yet integrated. Mission wiring and external effect adapters remain open.

The worker now also requires an initialized shared `DurableIdempotencyStore`. It claims the request ID across workers against a hash of the signed node ID and payload before start audit or handler dispatch. Completed requests return the stored result or error; concurrent copies report `REMOTE_IN_PROGRESS`, changed payloads report `REMOTE_REQUEST_CONFLICT`, and expired pending claims report `REMOTE_RECOVERY_REQUIRED`. The operator must reconcile uncertain effects before releasing an expired claim; never blindly rerun it. Terminal audit and idempotency completion happen after the handler, so a crash between effect and completion leaves a pending claim and requires recovery. Retention, capacity, and journal cleanup are store configuration decisions. The worker still does not autonomously recover external effects or integrate with missions.

Phase 2 progress: `ControlPlaneGateway` and `RuntimeGatewayDeployment` accept an optional `RuntimeRequestGuard`. Authorization runs before admission; the guard uses the actual socket address for its default identity, rejects excess requests, holds duplicate commands while one is running, and replays committed HTTP responses. A configured distributed limiter and durable idempotency store can extend these decisions across processes. Without them, limits and replay are local to the gateway instance. A failure to commit an idempotency response returns 503; the pending claim is retained after expiry because the command may already have executed. The Linux durable store now holds a kernel `flock` on an inherited file descriptor for each transaction; a short child acquires it, while the parent keeps the descriptor open until its journal operation finishes. A killed owner releases the lock. A local 12-claim comparison measured approximately 37 ms with this design versus 20 ms for the former directory lock and 805 ms for a separate Node transaction helper; this is a small overhead sample rather than a throughput claim. The lock file must remain at its configured path and this implementation requires Linux and the `flock` utility. Stop all older directory-lock processes before upgrading a shared journal because the old and new lock paths differ. Do not put raw forwarded identity headers into a trusted client key.

`FileRateLimiter` is an opt-in shared fixed-window implementation for the request guard. Configure the same file path, window size, and request limit on every process; one Linux kernel lock serializes state reads and atomic replacements. It hashes principals in the stored state, bounds retained principals, rejects corrupt or missing previously observed state, and keeps request decisions across restarts. The guard maps store errors to a fail-closed 503. A local 12-consume sample took approximately 49 ms; the default in-memory guard remains the faster choice when cross-process coordination is unnecessary. The file implementation requires a shared local filesystem with reliable `flock` semantics and is not a network-distributed rate service. Clock agreement matters across processes, and a response may have been allowed before an abruptly killed process writes its result; the counter is committed before `consume()` returns. A per-principal token bucket, identity-aware proxy integration, and load testing remain future work.

Expired pending idempotency claims now return `recovery_required` and the gateway responds with `IDEMPOTENCY_RECOVERY_REQUIRED` (409) without rerunning the command. The durable store preserves those claims through restart and compaction; its bounded record capacity can fill until an operator reconciles them. After verifying the external effect, an operator can call `reconcileClaim(key, fingerprint, token, response, { reason })` to record a replayable response, or `releaseClaim(key, fingerprint, token, reason)` only after confirming that no effect occurred. Both require the original token and an expired claim; normal completion rejects stale tokens. Direct deletion of pending claims is blocked. The in-memory guard also blocks expired claims during its process lifetime, but cannot survive a restart. Existing pending claims from older journals become blocked on upgrade and need reconciliation. This protects duplicate dispatch; it cannot determine whether an external effect occurred or undo one already committed.

`RuntimeBearerAuthorizer` is an optional concrete gateway authorization callback for opaque bearer tokens. A caller supplies `credentials()` that returns bounded `{ digest, principal, expiresAt, notBefore? }` entries; `digest` is the lowercase SHA-256 hex digest of a high-entropy token. The adapter checks a bounded token syntax, compares digests with constant-time byte comparison, and reads the provider on every request so rotation or revocation takes effect on the next call. It returns only the verified principal; its snapshot contains no credentials. The gateway removes Authorization and Proxy-Authorization headers before passing a request to its guard or command handlers. The provider must store digests outside public runtime configuration and serve a coherent list, and the listener must use TLS at the deployment boundary because bearer tokens grant access when disclosed. Invalid headers and expired tokens are denied, and provider failures fail closed. `ControlPlaneGateway` and `RuntimeGatewayDeployment` accept an optional `preAuthLimiter` with `consume(principal)`, called on the actual socket address before authorization. A shared `FileRateLimiter` can bound attempts across local processes, including invalid tokens; limiter failures return 503 without calling the credential provider. This optional limit charges every request, including successful requests and local health checks. Deployments choose its quota separately from the authenticated request guard.

Trusted proxy identity uses an explicit list of proxy IP addresses. When enabled, `RuntimeRequestIdentity` walks a bounded, validated `X-Forwarded-For` chain from the socket toward the client and selects the nearest untrusted hop; malformed or oversized chains fall back to the socket address. Pre-authorization admission always charges the socket address. Configure only proxies that overwrite or correctly append forwarding headers, and keep authenticated principals authoritative when available.

The in-memory request guard bounds active rate windows with `maxRateWindows` (default 10,000), fails closed on capacity, and reclaims expired windows. Expired completed replay records are reclaimed at capacity or on direct lookup; pending ambiguous claims remain retained. Routine admissions avoid scanning every retained principal, preserving constant work for the local guard until cleanup is needed.

Phase 2 local verification: `node scripts/benchmark-phase2.mjs 100` on Linux/Node 24.22.1 measured local guard median 0.01 ms (p95 0.03 ms, approximately 79,922 decisions/s), shared file rate limit median 3.89 ms (p95 6.46 ms, approximately 228 decisions/s), and durable claim plus completion median 5.44 ms (p95 8.51 ms, approximately 169 pairs/s). These are sequential local samples, not a concurrent service capacity guarantee. The tests cover multi-process contention, process death, stale claims, corrupt state, proxy spoofing, credential rotation, and replay. The local Phase 2 modules are integrated; multi-host coordination, TLS termination, credential storage, proxy deployment policy, and sustained production load tests remain deployment concerns.

The gateway authorization callback can return `{ allowed: true, principal: 'verified-user' }` to bind the request guard, replay key, and command context to an authenticated principal. Boolean `true` continues to authorize local traffic, which falls back to the socket address for guard identity. Raw `clientKey`, forwarding headers, and client ID headers do not establish a trusted gateway principal. A non-loopback listener requires an explicit authorization callback that returns a verified principal for each accepted request; returning only `true` receives 403. The callback must verify the credential or upstream authentication itself, and deployments must keep principal values stable across processes. Authentication providers, credential rotation, and trusted proxy integration are deployment-specific future work.

Phase 3 starts with opt-in `RuntimeEventTransport`: bounded asynchronous publishing, ordered event delivery, independent subscriber copies, explicit capacity rejection, and drain on close. The existing synchronous `EventBus` remains the local low-overhead path. An optional Linux `FileEventJournal` persists JSON events under a kernel lock before subscriber delivery and supports ordered replay across processes and restarts. Each record contains a SHA-256 chain link; replay verifies every record, sequence, and head, while append checks the tail in constant record work. The chain detects accidental or uncoordinated modifications during replay; it is not authenticated against an actor that can rewrite all journal files. The default capacity is 10,000 records and 64 KiB per event. Capacity rejects new writes rather than silently dropping history. A crash between record and head replacement leaves an orphan and fails closed; recovery requires an operator to inspect and reconcile the files. Replay scans the bounded journal, so this file implementation is intended for local durable control events rather than high-volume telemetry. It does not yet push events across processes or implement compaction and retention.

`FileEventConsumer` adds pull-based cross-process delivery for a named checkpoint path. `runOnce()` takes a Linux kernel lock across a bounded batch, invokes the listener in sequence, and persists the cursor after each successful call. Another process using the same checkpoint resumes where the first stopped. Startup verifies the full journal once; later reads verify the cursor hash and contiguous batch without rescanning all old records. A listener failure retains the previous cursor. A process crash after an external effect but before checkpoint commit can deliver the event again, so listeners must use an idempotency key such as the event sequence and journal identity at their own effect boundary. Missing or corrupt checkpoint state fails closed after initialization. This is at-least-once pull delivery on a shared local filesystem, not exactly-once effects or a network message broker.

Retention is explicit: `FileEventJournal.compactThrough(sequence, expectedHash)` verifies the retained chain, records a durable base anchor, and removes records through that sequence. It frees bounded record capacity without renumbering later events. Consumers behind the base receive `EVENT_JOURNAL_GAP` rather than silently skipping data. The operator must verify that every relevant consumer checkpoint has advanced before compaction, or deliberately accept that it must rebuild from another trusted source. A crash after the base anchor commits may leave old files to clean; repeating compaction at the same base removes them. This local policy does not automatically track all consumers or repair missing events.

`FileEventJournal.recoverOrphan()` is an explicit local repair for the narrow crash window after one complete record has been synced but before its head replacement. Under the journal lock, it verifies the retained committed chain, the orphan's sequence, previous hash, and payload hash, rejects a second orphan or capacity violation, then atomically advances the head. Missing or corrupt committed records remain blocked. Operators should inspect the interrupted producer before running repair, since promotion makes the recovered event available for at-least-once consumption.

`ObservabilityEngine` can subscribe to `RuntimeEventTransport` through `eventTransport` while retaining its existing synchronous `EventBus` option. The two sources cannot be configured together because that would double-count events. Metric series and active execution IDs now have explicit cardinality limits; excess metric names increment `metrics.dropped_series`, and the oldest active ID is evicted with `active_executions.evicted`. These counters make the bounded in-memory view's loss visible. A live subscription covers newly published events only.

For retained, unpruned history, `ObservabilityEngine.syncFromJournal(journal)` verifies the full chain on first sync and rebuilds metrics, traces, and recent events in order. Later calls use an in-memory hash cursor and apply only new events. It rejects an engine already subscribed to a live source to avoid double counting. A fresh engine after compaction gets `EVENT_JOURNAL_GAP`; a trusted metric and trace snapshot anchored to the journal base is required to restore lifetime aggregates after pruning. Sync takes a finite head target even if producers continue appending, and callers schedule subsequent syncs as needed.

`FileObservabilityCheckpoint` now persists an exported, bounded observability projection with an integrity digest and a monotonic journal sequence under a Linux file lock. To retain lifetime aggregates, sync the projection, `save(engine)`, then compact only through the saved sequence and hash. After restart, load the checkpoint, call `ObservabilityEngine.restoreCheckpoint(payload)`, then `syncFromJournal(journal)` to verify the retained chain and apply later events. Saving the checkpoint before compaction ensures a crash between those steps leaves a recoverable older journal. A missing or altered initialized checkpoint fails closed. The digest detects accidental changes; it does not authenticate against an actor with write access to the files. Multiple independent projections need their own checkpoints and retention coordination.

Phase 3 local performance evidence: `node scripts/benchmark-phase3.mjs 100` on Linux/Node 24.22.1 measured 100 sequential append samples at median 5.91 ms (p95 8.29 ms, about 161 operations/s), 100 incremental one-event reads at median 2.55 ms (p95 4.19 ms, about 362 operations/s), and five full replays of 101 records at median 21.87 ms (p95 24.57 ms). These are small local overhead samples, not concurrent capacity guarantees. Each operation spawns a short `flock` helper and syncs file replacements; use this path for durable control events, not high-volume telemetry. Journal record and checkpoint writes use compact JSON so the enforced byte limits agree with replay. A network transport, authenticated integrity against malicious file writers, automated consumer-aware retention, and deployment load tests remain outside this single-host file implementation.

Phase 3 local shared-file scope is integrated: durable publish-before-delivery, hash-linked replay, cross-process at-least-once consumption, explicit retention with visible gaps, validated orphan recovery, bounded observability, and anchored projection restore after compaction. A killed-consumer test confirms that an uncommitted effect is retried after process death. This does not make external effects exactly once; consumers enforce their own idempotency. Multi-host delivery and hostile-writer protection require deployment-specific infrastructure and are not claimed as complete.

Lifecycle startup rolls back components that successfully started, and stop attempts every component even if one fails (#136). `RuntimeDeploymentHost` composes lifecycle, bounded incident polling, failover attempts, and drain, with optional signal wiring (#137). Startup rollback calls stop on components whose start completed, in reverse dependency order. A component whose start throws must clean up its own partial initialization. If rollback or shutdown cleanup fails, restart remains blocked until a subsequent stop successfully cleans up components; operators can inspect `cleanupRequired` in the lifecycle state. Component start and stop handlers must be safe to retry because cleanup after an uncertain failure may revisit a component.

Runtime configuration is limited to validated, non-secret settings with monotonic versions and atomic reload. Secret-shaped fields are rejected; credentials require a separate secret provider and must not enter configuration snapshots or history.

The failover file store writes a persistent `.initialized` marker under its lock before the first state write. An initialized store with a missing state file fails closed even for a new process, preventing epoch reset. Existing valid state files acquire the marker on first access. Keep the marker with the state and lock files; restore lost state from a trusted backup. A crash between marker creation and initial state write also requires repair rather than an unsafe fresh claim.

`FileIncidentProvider` reads a bounded, UTF-8 JSON document `{ "schemaVersion": "0.1.0", "incidentId": "operator-stable-id", "active": true }` through a retained descriptor. A deployment controller must atomically replace this document with a new unique ID for each independent incident; set `active: false` to pause recovery. Point `RuntimeDeploymentHost` or `RuntimeGatewayDeployment` at `provider.provider()`. Missing, corrupt, and oversized files report errors instead of generating a transient incident ID. Reusing an ID after a committed recovery will suppress that recovery, so the publisher must own incident identity and persistence. This is a concrete file-backed provider for a single shared filesystem, not an automatic incident detector or a multi-host consensus service.

For a Linux shared-file deployment, `FileIncidentController` can publish those IDs: `open()` acquires a kernel lock and returns the existing active ID or creates a UUID, while `resolve(id)` deactivates only that matching active ID. Separate processes therefore agree on one active incident, and a later incident receives a new ID. Its initialization marker prevents a missing state file from silently resetting identity after first use. A deployment health detector still chooses when to call `open()` and `resolve()`; do not resolve merely because a recovery callback returned if the underlying failure persists. Keep the state, `.lock`, and `.initialized` files on a filesystem with reliable Linux `flock` semantics.

`RuntimeResourceGovernance` tracks in-process reservations. Its `cpuMs` and `memoryBytes` values represent requested budgets, not measured consumption or OS-enforced limits. `ToolRuntime` can optionally admit a manifest-declared reservation before dispatch and hold it until the handler settles, even if the caller times out. When configured with `BoundedHttpTransport`, a tool receives `context.network.request()`, which charges each attempt against the manifest's `resourceRequest.networkRequests`, restricts exact origins and redirects, bounds response bytes, and forwards cancellation (#142). A caller cannot raise this manifest budget through context. Arbitrary handler use of global fetch, HTTP libraries, or raw sockets bypasses this adapter; hard egress enforcement requires isolation outside the process. `MeasuredProcessRuntime` is a separate opt-in path for trusted JavaScript modules: a child supervises a worker thread's measured CPU and JS heap, while the parent terminates the child on wall deadline and caps concurrent children. On Linux, an optional `rssBytes` cap samples the child process's resident high-water mark, including native Buffer allocations (#139). `createMeasuredProcessHandler` lets a registered tool use this path and forwards cancellation. The child contains a worker heap crash. Sampling can overshoot by one interval, and RSS is measured inside the child rather than enforced by the OS; a very fast or extreme allocation may exceed the cap before termination. This path requires Node 22.19+ for worker CPU measurement, fails closed if a requested measurement is unavailable, and is not a security sandbox or hard network quota. Other tool handlers do not automatically run inside it. Do not use independent resource governors as a shared quota.

Failover callers must supply a stable incident ID and a recovery callback. `RuntimeFailoverKernel` gates callbacks on a failed supervisor evaluation, renews its lease during recovery, and commits an incident result only under its current epoch and token. A later incident ID permits a new recovery. Recovery callbacks receive an abort signal and a fence with `key`, `epoch`, `token`, and `assertCurrent()`. `FileFailoverStore.writeFencedJson(fence.key, fence, destinationPath, value)` is a concrete local file effect boundary: the same Linux lock validates the active lease immediately before atomic replacement, so an expired holder cannot write after takeover (#138). The destination must be trusted configuration, separate from failover state; callers should not accept arbitrary user paths. A network service, database, or other effect adapter must enforce the epoch and token at its own commit boundary. An uncooperative callback may continue its external work after timeout or cancellation, and a completed file effect cannot be rolled back if the recovery result later fails. The deployment host is opt-in and requires a deployment-specific incident provider and recovery callback.

`RuntimeGatewayDeployment` is a concrete local HTTP composition. It starts and stops `ControlPlaneGateway` through lifecycle, keeps an admission lease until each HTTP response finishes or closes, and checks control-plane health through the supervisor. Shutdown rejects new HTTP requests with 503 while active responses drain. The default listener binds 127.0.0.1; another bind address requires an explicit authorization callback. A caller must provide a durable failover store, stable incident identity, and recovery callback suited to its deployment. The composition does not infer incidents from transient health timestamps or automate arbitrary external effects.

Phase 1 evidence: `deployment-host.test.js` kills a process after it claims recovery, starts a replacement host, and verifies takeover after lease expiry. `node scripts/benchmark-phase1.mjs 12` on Linux/Node 24.19.0 measured 12 local samples: claim plus release median 155.04 ms (p95 179.59 ms); measured echo median 123.44 ms (p95 130.95 ms); measured echo with RSS median 125.52 ms (p95 133.36 ms). This small local run is an overhead reference, not a throughput guarantee. Each file store operation spawns a locked helper, and each measured task spawns a child. These paths are opt-in and should not be placed on a high-volume hot path without a persistent coordinator or worker pool and a separate performance review. Native RSS sampling is not a hard memory limit. Phase 1 remains open for deployment-specific adapters and stronger OS-enforced limits where required.

`RemoteWorkerCoordinator` composes a stable execution ID, explicit request ID, `FileFailoverStore` lease, Unix client, and durable result commit. It returns an already committed matching result without dispatch. A transport failure retains its lease until expiry because the worker may have performed an effect. The shared worker idempotency ledger uses the request ID across nodes; moving an uncertain request to another node conflicts or requires reconciliation rather than running a second effect. The coordinator does not renew leases during long-running work: choose a lease longer than the bounded task duration, and enforce the file fence at every configured effect. Its file-store helper overhead is unsuitable for high-volume dispatch without measurement. A network coordinator, worker attestation, mission wiring, and non-file effect adapters remain open.

Phase 4 audit hardening: the shared idempotency journal now creates a persistent initialization marker before its first append. A restarted process fails closed if an initialized journal disappears; retain the marker with the journal and lock. The Unix worker validates that a handler result is JSON serializable and within its response byte budget before recording a terminal success. Oversized results become a replayable failure, so repeating the request does not rerun the handler. Effects performed before output validation still require reconciliation.

`createRemoteMissionTaskHandler({ coordinator })` now connects a single explicit mission task capability to the remote coordinator through `TaskGraphExecutor.executeTask`. It derives stable bounded task and request IDs from the mission execution and task IDs, so recovery reuses the worker idempotency identity. Transient transport and ownership conflicts leave the mission resumable, and the existing mission verifier still validates the graph output before delivery. This adapter does not send arbitrary callbacks or code to a worker. The current `ExecutionStateStore` is process-local; restart recovery needs a durable task graph state adapter and a full cross-process interruption test. Cancellation of a graph does not stop a remote handler already running; effect fencing and idempotency remain the final safety boundary.

Phase 4 restart hardening: `FileExecutionStateStore` now reloads under a Linux kernel lock on every operation, applies atomic replacements with a byte and record limit, and retains an initialization marker so a new process rejects missing state. Existing valid state files acquire a marker on first read. Keep the state, `.flock`, and `.initialized` files together on a filesystem with reliable `flock`; a missing or corrupt initialized file requires trusted repair. `TaskGraphExecutor` now passes the expected state version on every write and serializes its parallel task writes, rejecting a stale host instead of overwriting a newer recovery state. A new mission engine with a recreated file state store resumes the same stable remote request identity. The test recreates objects in one process; killed-process socket and effect tests remain to be added.

Phase 4 crash injection: a separate worker process is killed after a configured fenced file effect and before it can complete its request. A replacement process reloads the nonce, audit, and idempotency stores; after the pending claim expires, the same signed operation with a fresh nonce returns `REMOTE_RECOVERY_REQUIRED` and the effect remains single. This verifies the ambiguous-effect path on a Linux Unix socket. The operator still needs to reconcile the pending claim against the persisted effect. It does not establish exactly-once behavior for arbitrary external effects.

Phase 4 response authentication: the Unix worker signs every parseable request outcome with a domain-separated HMAC over the response type, request ID, node ID, original request nonce, and result or error. The client verifies the MAC and correlation before accepting even an error, so a forged or replayed response cannot masquerade as a current request. Malformed requests without a valid response context close the socket. Output byte checks now include the signed frame before recording a successful claim. This proves possession of the shared key and protects response integrity; it is not hardware attestation or encryption. Use a private socket or TLS for confidentiality, and separate keys by worker trust domain.

`TlsWorkerBridge` exposes the existing governed Unix worker over TLS 1.3 with mandatory client certificates, CA validation, an explicit client-certificate SHA-256 allowlist, bounded connections and frames, timeouts, and backpressure. `TlsWorkerClient` validates the server certificate chain, DNS name, and pinned SHA-256 fingerprint, then verifies the signed worker response. Certificates and keys are supplied by deployment secret management; the implementation does not generate or persist production credentials. A CI test creates short-lived test certificates and checks valid dispatch, a wrong server pin, and an unlisted client certificate. This provides a protected network hop, but distributed replay/lease/idempotency guarantees require reliable shared storage or a transactional coordination service accessible to every participating host. The current file stores are only proven on a single shared Linux filesystem; the TLS bridge alone does not make them multi-host safe. Certificate rotation, revocation, network partition fault injection, and load measurement remain deployment work.

Phase 4 local overhead sample: `node scripts/benchmark-phase4.mjs 20` on a GitHub Actions Linux runner with Node 22.23.4 measured 20 sequential governed echo requests, excluding certificate generation and warmup. Direct Unix dispatch median 29.05 ms, p95 32.89 ms, approximately 34.1 operations/s; the TLS loopback bridge median 34.77 ms, p95 36.53 ms, approximately 28.8 operations/s. Each request performs durable nonce, audit, and idempotency writes. These small sequential loopback samples are not network capacity, concurrency, or production latency guarantees; run deployment-specific load tests before choosing concurrency and timeouts.

The TLS bridge supports an atomic, bounded replacement of its client-certificate fingerprint allowlist via `rotateClientFingerprints()`. Add the new client pin alongside the current pin, roll out the client certificate, then replace the allowlist with only the new pin. New connections use the latest list; active sessions complete unless the bridge is stopped. `TlsWorkerClient` accepts `serverFingerprints256` for a bounded overlap during server certificate rotation (or the original single `serverFingerprint256`). Construct new clients with the final pin set after rotation. The CA and certificate/key are still deployment-managed, and a bridge restart is required to load a new server certificate or CA. Revoking a pin cannot invalidate an already established request; use `stop()` for immediate session termination. The worker HMAC key and shared durable stores require independent rotation and remain necessary for request integrity.
